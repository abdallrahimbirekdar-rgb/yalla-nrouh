# تجربة الرحلة قبل رفع يلّا نروح

## اختبار معزول يمكن تكراره

من مجلد المستودع، بعد تثبيت متطلبات المشروع، شغّل الاختبارات التالية باستخدام Node.js 22 أو أحدث.

```sh
npm test
qa_deps="$(mktemp -d)"
npm install --prefix "$qa_deps" --no-audit --no-fund @electric-sql/pglite@0.5.15
NODE_PATH="$qa_deps/node_modules" node --experimental-strip-types scripts/verify-ride-qa.mjs
```

ينشئ الاختبار قاعدة PostgreSQL مؤقتة وحسابات وهمية للسائق والزبون وحسابًا خارج الرحلة. يعيد توجيه طلبات عميل التطبيق إلى القاعدة المؤقتة. يستخدم دوال المشروع للتحقق من الاعتماد، قبول الطلب، تحديث موقع السيارة، إكمال الرحلة وحجب سبب الإلغاء وموقع السيارة عن أي حساب خارج الرحلة. يحاكي ضياع الرد بعد تسجيل الطلب والإلغاء في القاعدة. ويؤكد أن إعادة الطلب بنفس المعرّف لا تنشئ رحلة ثانية. يستخدم بيانات عرض ومسافة اصطناعية، ويتحقق من إغلاق الرحلة وحذف الحسابات في الاختبارات المعزولة.

## تجربة Android على هاتفين

تحتاج التجربة إلى نسخة موقع على بيئة اختبار لها Supabase منفصل وإعداد خرائط خاص بها. يختبر المسار من حساب سائق معتمد وحساب زبون فقط.

1. يرسل السائق بيانات السيارة. تطلب الإدارة تعديلًا مع سبب. يعدّل السائق البيانات ويعيد الإرسال ثم يُعتمد.
2. يطلب الزبون التاكسي ويقبله السائق. عند تحرك السائق، تحقق من مكان السيارة، النقطة الزرقاء لموقع الزبون، وصول خط الاقتراب إلى نقطة الالتقاء، وتحديث الوقت والمسافة. جرّب استئناف الخريطة بعد تصغير التطبيق.
3. افصل الإنترنت بعد ضغط تأكيد الطلب وقبل رؤية الرد. عند العودة، تحقق من ظهور نفس الطلب. أعد التجربة مع زر الإلغاء، من حساب السائق ومن حساب الزبون. تحقق من السبب في سجل كل طرف.
4. في رحلة أخرى، جرّب تسجيل الوصول، بدء الرحلة، وإنهاءها من هاتف السائق. بعدها تحقق من انتهاء عرض موقع السيارة للزبون.

قبل نشر هذه الواجهة، تُطبّق ترحيلات قاعدة البيانات اللازمة لفرع الجاهزية، ومنها `backend/ride-cancellation-details.sql` بعد ترحيل تسجيل أسباب الإلغاء. هذه الدالة ترجع الأسباب فقط لطرفَي الرحلة.
